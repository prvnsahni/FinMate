# ADR-025 — P2P direct-ledger counterparty identity and claim/merge resolution

- **Status:** Accepted (records an already-implemented engineering decision) · **Implementation state:** PARTIAL — storage + read-time resolution shipped (P2P-1 `9e93920`, P2P-2 `937b38b`); **P2P-3 API exposure NOT built and GOVERNANCE-BLOCKED** · **Date:** 2026-09-07
- **Decision:** A group-less direct-ledger obligation (`direct_ledger_entries`) may be between a registered `User` and a non-member `Contact`. Each side carries **exactly one identity — `User` XOR `Contact`** — mirroring the dual-identity model already used by `expense_splits` / `expense_payments`. A `Contact` is the existing non-authenticated **financial participant** identity: it is **not** an authentication principal, **not** a `GroupMember` with access, and **not** a new "Person" entity, and **no fake `User`** is created for it.
- **Immutability + resolution:** Historical `DirectLedgerEntry` rows are immutable financial history. Contact→User **claiming** and Contact **merge redirects** are resolved **at read time** during ledger assembly (`PersonLedgerService`): a claimed Contact folds to its terminal `User` identity, a merged Contact resolves through the existing `ContactsService.resolveMergeRedirect` chain (incl. `A→B→C` and `A→B→C→claimed-User`); claimed/merged history therefore **collapses into the terminal identity** for reads. **No historical financial row is rewritten, copied, or deleted** merely because a Contact is claimed or merged.
- **Ledger keys:** opaque strings `user:<id>` / `contact:<id>` — no business meaning enters the calculator.
- **Context:** People/P2P was `User`-only; the reusable, claim-able, merge-able `Contact` identity already exists (CNT-1/CNT-2) and is proven in groups (`6a88ecd`/`deef616`).
- **Alternatives considered:** (a) new `Person` entity — rejected (duplicates `Contact`; breaks GOV-1 additive-baseline); (b) fake `User` for a Contact — rejected (auth-principal pollution); (c) rewrite ledger rows on claim/merge — rejected (violates financial-history immutability + GOV-1); (d) **chosen** — additive `User XOR Contact` + read-time resolution.
- **Security impact:** no new auth principal; a Contact never gains group access. **P2P-3 API exposure must caller-scope Contact access and resist IDOR** (see Decision Ledger **P2P-CNT-3**).
- **Privacy impact:** Contact rows are non-user third-party PII (CNT-1). P2P surfaces **`displayName` only** — never Contact email/phone, internal Contact id, or provenance; **no global Contact directory or name-only search**. The lawful basis for storing/exposing non-user Contact PII and the non-user rights process remain **`[COUNSEL REQUIRED]`** (GOV-4: no compliance claim). This ADR asserts **no** legal determination.
- **Finance/parity impact:** `simplifyLedgerDebts`, `calculateDeterministicSplits`, and the finance-golden fixtures are **unchanged**; the FIN-002 parity gate is run each implementation batch (ADR-017). Existing `User↔User` behaviour is byte-for-byte unchanged.
- **Backward-compatibility impact:** additive migration `1720400000000` relaxes `from_user_id`/`to_user_id` to nullable and adds nullable `from_contact_id`/`to_contact_id` (+ per-side XOR checks, same-kind distinctness check); existing `User↔User` rows are untouched; `down()` is guarded (refuses to delete Contact-backed history).
- **Deletion impact:** reconciles **DEL-1** — nullable user FKs do **not** weaken "anonymize-in-place, never row-DELETE." `created_by_user_id` stays NOT NULL; contact-backed rows are likewise never deleted and are redirected/pseudonymized at read time (see Decision Ledger **P2P-CNT-4**).
- **API exposure (P2P-3):** exposing Contact-backed counterparties through the P2P API is **subject to the Contact non-user PII/privacy boundary** and remains blocked pending the governance-owner + counsel sign-off recorded in **P2P-CNT-3**.
- **Requires approval before P2P-3:** `[COUNSEL REQUIRED]` legal basis + non-user rights process (CNT-1/GOV-4); governance-owner authorization of the API privacy/authz boundary (P2P-CNT-3). Neither is satisfied by this ADR or by the engineering implementation.
- **Dependencies:** CNT-1, CNT-2, GOV-1/2/4/5, ADR-016 (mixed-state P2P), ADR-017 (parity), ADR-019/DEL-1 (deletion), ADR-024 (Zone-2 finance).
- **Related Ledger items:** P2P-CNT-1, P2P-CNT-2, P2P-CNT-3, P2P-CNT-4 (2026-09-07 addendum); CNT-1, CNT-2, DEL-1.
- **Related architecture docs:** Data Classification Matrix §5.7 (`direct_ledger_entries`) + §5.13 (`contacts`); Processing Activities Register (Contacts / People-P2P rows).
- **Simple explanation:** You can now record lending with someone who has no FinMate account (a "Contact"). If they later sign up or you merge two duplicates, FinMate just _reads_ the old records as pointing to the right person — it never edits your financial history. Their private details (phone/email) are never shown through the People screens, and turning any of this into an API still needs a privacy/legal sign-off.
- **Technical explanation:** `DirectLedgerEntry` is `User XOR Contact` per side (DB-enforced). `PersonLedgerService` builds the ledger under opaque `user:`/`contact:` keys and, at read time, folds `claimedByUser` and follows `mergedIntoContact` to the terminal identity (cycle-guarded), collapsing history into one `CounterpartyLedger`. Rows are never mutated; the FIN-002 calculators are untouched; P2P-3 API exposure is gated by P2P-CNT-3.
